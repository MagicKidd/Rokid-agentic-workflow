# 社区方案深度调研 (Community Solution Research)

## 核心原则 (Core Principle)
**"带着痛点去查，不要泛泛而搜"**
在外部社区寻找方案之前，必须先将内部的业务痛点和工程约束翻译为技术锚点。外部调研的终极目的是解决我们自己的问题，而不是写一篇学术综述。

## 执行流程 (Execution Flow)

### Step 1: 内部约束提取 (Constraint Extraction)
如果用户没有明确提供，你必须先通过 `agent-transcripts` 或项目文档提取以下要素（这一步是必须的，禁止跳过）：
- **核心痛点**：当前系统哪里不行？（如：大模型意图路由太慢，要 850ms）
- **工程约束**：我们有什么客观限制？（如：只能用本地 CPU、必须无网运行、不允许引入重型框架）
- **技术栈基建**：我们正在用什么？（如：we already have a Postgres database and Redis cache）

### Step 2: 搜索策略构建 (Search Strategy)
禁止使用单纯的中文自然语言泛搜（如 "意图识别怎么做"）。必须使用多维度的专业搜索组合：
- **架构与标准类**："[技术栈] architecture" / "[关键词] system design" / "[关键词] best practices"
- **落地与避坑类**："[关键词] in production" / "[技术栈] challenges" / "[关键词] vs"
- **真实讨论类**："[关键词] reddit" / "[关键词] stack overflow"
- **开源生态类**："[关键词] github" / "awesome [关键词]"
*使用 `parallel-web-search` 或 `parallel-deep-research` 并发执行上述高维度的查询。*

### Step 3: 方案筛选与交叉验证 (Cross-Validation)
这是体现你超级智能体价值的一环。对搜索到的每个潜在方案，用 Step 1 提取的内部约束进行残酷过滤：
- 这个方案能解决我们的核心痛点吗？
- 它是否超出了我们的工程约束？（太重？太贵？需要大量标注数据？维护成本太高？）
- 它能否无缝融入我们现有的技术栈？还是需要推倒重来？

### Step 4: 结构化输出调研报告 (Output Format)
必须按照以下模板向用户输出最终的调研报告：

```markdown
## 社区调研报告：[主题名称]

### 1. 我们的内部锚点
- **核心痛点**：...
- **工程约束**：...
- **现有基建**：...

### 2. 社区主流方案全景概览
- **方案 A** (如：Semantic Router)：[一句话原理]
- **方案 B**：[一句话原理]
- ...

### 3. 方案适配性残酷对比 (Crucial)
| 候选方案 | 解决痛点程度 | 违背约束情况 | 接入成本 | 最终推荐度 |
|---|---|---|---|---|
| A | 完美解决延迟 | 无 | 极低（复用现有基建）| ⭐⭐⭐⭐⭐ |
| B | 准确率高 | 需引入新重型依赖 | 高 | ⭐⭐ |

### 4. 落地建议与避坑指南 (Actionable Insights)
- **结论**：结合我们的项目现状，强烈建议采用 [方案X]，原因如下...
- **社区踩坑预警**：根据社区反馈，实施该方案时通常会遇到 [阈值难以校准] 的问题，建议我们在落地时...
```

## 注意事项
- 坚决淘汰那些虽然理论先进，但严重违反我们系统约束的“屠龙术”方案。
- 如果搜索结果都是泛泛而谈的 SEO 营销文章，立即调整关键词，强制加上 `github`、`issue` 或具体的技术专有名词后缀重新搜索。
